## Сценарий

От настройки расписания до записи в календаре владельца — один непрерывный путь из двух ролей: **Владелец** и **Гость**.

### Владелец

1. Владелец задаёт общее расписание: доступные дни недели и время внутри дня. Расписание одно на аккаунт — все типы встреч наследуют его.
2. Создаёт тип встречи: указывает название, описание и длительность _(например: Консультация — 30 минут)_.
3. Копирует ссылку на этот тип встречи и делится ею с другими пользователями.

### Гость (переходит по ссылке, регистрация не нужна)

4. Видит календарь с доступными днями и временными слотами; слоты показаны в часовом поясе, взятом из настроек браузера (то же — для владельца).
5. Выбирает день и слот — слот блокируется для остальных пользователей на время бронирования.
6. Вводит имя и email: без них запись не подтверждается.
7. Видит экран успешного бронирования с деталями встречи (тип, дата, время, часовой пояс, владелец) — либо информативное сообщение об ошибке, если слот уже занят.
8. Если бронирование не завершено, слот автоматически снова становится доступен для записи.

### Владелец (результат)

9. Успешная запись сразу появляется в разделе «Записи»: гость (имя и email), тип встречи, дата и время — без необходимости подтверждать её вручную.
10. Запись можно отменить или изменить; отменённая остаётся в списке с пометкой, а освободившийся слот снова доступен для записи.

## Стек

TypeScript 7, Node.js 26 LTS, Fastify, React, Vite и Mantine.
Контракт TypeSpec компилируется в OpenAPI, Hey API генерирует Fetch SDK.
Зависимости организованы в Yarn workspaces с общим `yarn.lock`.

```text
apps/api/             — запускаемый бекенд Fastify
apps/web/             — запускаемый фронтенд Vite + React + Mantine
packages/api-client/  — библиотека с клиентским SDK
contracts/            — исходный TypeSpec и сгенерированный OpenAPI
```

`apps` содержит приложения с собственным запуском, `packages` — импортируемые
библиотеки. Фронтенд обращается к серверу через SDK, без импорта серверного кода.

## Установка

Установите [mise](https://mise.jdx.dev/getting-started.html) версии 2026.11.8 или новее.
Все остальные версии закреплены в `mise.toml`; отдельно устанавливать Node или Yarn не нужно.

```bash
git clone https://github.com/AndrewVdovichenko/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install
mise run setup
```

`setup` устанавливает зависимости по lock-файлу, генерирует SDK, скачивает браузер
chromium для e2e-тестов и подключает hk
только для этого репозитория. Для локальной PostgreSQL установите
[Apple Container](https://github.com/apple/container) (macOS с Apple silicon).
Запустите БД и отдельно примените миграции:

```bash
mise run db:start
mise run db:migrate
mise run owner:password
```

Команда пароля требует терминал, скрыто запрашивает пароль дважды и принимает
не менее 12 кодовых точек Unicode, включая пробелы и кириллицу. Пароль нельзя
передавать аргументом. Успешный сброс отзывает все сессии; ошибка сохраняет доступ.
До настройки пароля публичная часть работает, вход Владельца закрыт.
Страница входа — `/owner/login`; каждый вход создаёт независимую сессию
на семь суток без продления. Выход завершает только текущую сессию.

Локально и в CI используется `postgres:18.7`. Именованный том `calendar-postgres`
монтируется в `/var/lib/postgresql` и сохраняется при остановке и пересоздании
контейнера. `mise run db:stop` останавливает БД, `mise run db:status` показывает
контейнеры. Локальный порт привязан к `127.0.0.1:5432`; режим `trust` предназначен
для разработки на этой машине. Production требует отдельной защищённой БД
с паролем, `DATABASE_URL` из окружения и `APP_ORIGIN` с HTTPS.
Production-прокси должен передавать `/api` серверу без переписывания префикса.

Необязательная `.env` загружается сервером и командами управления из корня проекта;
пример переменных — [.env.example](.env.example). Секреты не коммитятся.
`APP_ORIGIN` должен точно совпадать с источником браузера (по умолчанию
`http://127.0.0.1:5173`). Все изменяющие запросы требуют этот `Origin`.
`TRUSTED_PROXIES` — явные IP/CIDR доверенных прокси через запятую; по умолчанию
прокси не доверяются, `X-Forwarded-For` не влияет на ограничение входа.

Миграции находятся в `apps/api/migrations`: версии и SHA-256 фиксируются
в БД в одной транзакции с изменениями схемы, исполнители сериализуются блокировкой.
Применённые SQL-файлы нельзя изменять; добавляйте следующую версию.
API проверяет схему до открытия порта, автоматически её не меняет и при ошибке
завершает запуск. Недоступность БД после запуска возвращает временную ошибку.
Пул ограничен десятью подключениями; ожидание подключения и блокировки — 3 с,
SQL — 5 с, вся транзакция — 10 с через `transaction_timeout` PostgreSQL 18.

Бекенд принимает `HOST` и `PORT` (по умолчанию `127.0.0.1:3000`). В production
он слушает `0.0.0.0`, раздаёт собранный фронтенд и проверяет БД на `/health`.
Для согласованного запуска через daemons используются порты 3000 и 5173.

## Docker и публичный сервис

Образ собирается по корневому `Dockerfile` и включает API, собранный фронтенд
и SQL-миграции. Проект Railway включает веб-сервис, собираемый из корневой
Dockerfile, и управляемую базу PostgreSQL 18; их связывает ссылка
`${{Postgres.DATABASE_URL}}`, проверка живости — `/health`. При старте
контейнер применяет миграции, если задан `DATABASE_URL`, и запускает
сервер на порту из `PORT`. Production-режим включает переменная
`NODE_ENV=production` из конфигурации сервиса — в образе её нет; в этом
режиме обязательны `DATABASE_URL` и `APP_ORIGIN` с HTTPS, а без них образ
стартует в demo-режиме без БД (так его запускает hexlet-check). На Railway
`APP_ORIGIN` можно не задавать: используется `RAILWAY_PUBLIC_DOMAIN` со схемой
`https://`. Для локальной проверки с PostgreSQL задайте
`APP_ORIGIN=http://localhost:8080` и `PORT=8080`; production требует HTTPS,
поэтому локальный HTTP-запуск выполняйте с `NODE_ENV=development`.

Публичный адрес развёрнутого сервиса:
**https://calendar-386-production.up.railway.app**. На нём проверены
гостевой сценарий (выбор слота, холд и подтверждение брони) и сценарий
Владельца (вход по паролю, просмотр броней, выход).

Новый код разворачивается в том же сервисе: переключение источника
на этот репозиторий — отдельная задача
[#2](https://github.com/AndrewVdovichenko/ai-for-developers-project-387/issues/2).

Конфигурация Railway MCP для Codex лежит в [`.codex/config.toml`](.codex/config.toml).
Она использует команду CLI `railway mcp` без токена в репозитории.
Установите Railway CLI и выполните `railway login`; сессия хранится вне Git.

Пароль владельца настройте командой `mise run owner:password`, временно задав
`DATABASE_URL` удалённой БД и `APP_ORIGIN` публичного адреса в локальном
окружении. Команда запрашивает пароль скрыто и не принимает его аргументом.

Записи хранятся в PostgreSQL и **не сбрасываются при перезапуске
веб-контейнера**. Бесплатный тариф Railway даёт $1 месячного лимита:
сервисы и база засыпают после 5–10 минут без запросов и просыпаются
при обращении, сохраняя данные. После 30 дней триала с разовыми $5 проект
нужно перевести на бесплатный или платный план, иначе сервисы остановятся.

## Использование

```bash
mise run dev          # запустить оба сервера в фоне
mise run dev:status   # состояние процессов
mise run dev:logs     # журналы
mise run dev:stop     # остановить серверы
```

Откройте <http://127.0.0.1:5173> — это главная страница сервиса: оттуда CTA ведёт
в публичный каталог `/event-types`. Карточка ведёт на страницу выбранного типа
`/booking/:id`; выбор дней и слотов добавляется следующим этапом.
Название и описание Типа встречи хранятся как обычный PostgreSQL `text`.
U+0000 отклоняется при валидации в браузере и API с ошибкой рядом с полем;
остальные Unicode-символы и переносы строк поддерживаются.
В `/owner/event-types` вошедший Владелец создаёт сразу опубликованные Типы встречи
и копирует прямые ссылки. При неизвестном исходе создания действие
«Проверить результат / повторить» восстанавливает прежнюю операцию без дубликата.
До отправки ключ и поля сохраняются в localStorage, затем в sessionStorage;
запасная техническая cookie содержит только ключ и отпечаток параметров.
Если поля утрачены, повтор требует исходного ввода. Полный отказ хранилищ
блокирует отправку.
Vite перенаправляет `/api` на бекенд, сохраняя префикс.
Прямой адрес бекенда: <http://127.0.0.1:3000>.

```bash
mise run generate    # TypeSpec → OpenAPI → SDK
mise run build       # сборка бекенда и фронтенда
mise run check       # все проверки, тесты и сборка
mise run fix         # исправить форматирование
mise run security:audit # проверка yarn.lock по базе OSV (нужна сеть)
```

Изменяйте контракт в `contracts/main.tsp`, затем выполняйте `mise run generate`.
Каталоги `contracts/generated` и `packages/api-client/src/generated` создаются
генераторами: ручные правки и устаревшие результаты обнаруживает `check`.
Результаты генерации добавляются в коммит вместе с контрактом.

Vitest проверяет настоящий HTTP API через SDK, миграции и сессии на PostgreSQL.
Проверки серверных команд используют отдельные процессы и настоящий PTY
через `python3` (нужен Python 3, доступный в macOS и образе Ubuntu CI).
Каждый тест создаёт отдельную случайно именованную БД и удаляет только её.
`TEST_DATABASE_URL` задаёт административное подключение с правом `CREATEDB`
(по умолчанию локальная PostgreSQL, БД `postgres`). Это отдельная переменная:
тесты никогда не очищают `DATABASE_URL`. Тестовая `.env` автоматически не читается;
экспортируйте `TEST_DATABASE_URL` при использовании другого сервера.
Playwright (`mise run test:e2e`) проверяет e2e-сценарии фронтенда на chromium против
собранного `vite preview`: главную, навигацию, вход, выход, ошибки и безопасный
возврат. На прогон создаётся отдельная БД, API на порту 3001 и SPA на 4174;
один worker исключает совместное изменение тестового календаря.
При остановке тестового API БД удаляется. Подмены API для успешных сценариев нет;
сетевые сбои воспроизводятся прерыванием запроса браузером.
`mise run test:persistence` отдельно проверяет пересоздание PostgreSQL в Apple
Container с тем же томом: пароль, сессии, исходные сроки, отзыв, окно входа,
Типы встречи и результаты операций (успехи и окончательные отказы).
Команда создаёт собственные случайно именованные контейнер и том, затем удаляет
их. Она требует Apple Container и поэтому не входит в платформонезависимый `check`.
Сборка Vite не заменяет проверку типов: TypeScript проверяется отдельно в strict-режиме.

Компиляция и проверка типов выполняются TS 7 (`tsc`). Hey API и dependency-cruiser
используют программный API TS 6: для них в корне установлен официальный пакет
`@typescript/typescript6` под именем `typescript`. Пакет `@typescript/native` —
алиас TypeScript 7, предоставляющий корневую команду `tsc`; это не nightly-preview.

Для изолированной разработки календаря Слотов и будущей формы Гостя запустите
`mise exec -- yarn workspace @calendar/web storybook` (порт 6006).
В панели Storybook переключаются светлая и тёмная схемы Mantine; истории показывают
доступные Слоты, DST-повтор, переход даты, загрузку, пустоту, ошибку и устаревшие данные.
Статическая сборка: `mise exec -- yarn workspace @calendar/web build:storybook`.
Приёмочные проверки интерфейса остаются в Playwright против настоящего API;
тестовый сервер использует фиксированное время сезонного перевода часов.

## Проверки качества

`mise run check` запускает проверку генерации, Oxlint, oxfmt, TypeScript, Knip,
dependency-cruiser, syncpack, Betterleaks, jactionlint, Vitest, сборку и Playwright e2e.
Перед коммитом hk проверяет форматирование и линт изменённых файлов и секреты
в staged-изменениях; перед push запускает полный `check`. Автоисправления в хуках отключены.
GitHub Actions вызывает ту же команду на каждый push и pull request.
Проверка уязвимостей OSV запускается отдельно еженедельно и вручную; Dependabot
предлагает обновления npm-зависимостей и GitHub Actions.

Набор выбран по [dev-quality-gates](https://github.com/mokevnin/dev-quality-gates).
Результаты проверки инструментов и ограничения описаны в [отчёте](docs/quality-gates.md).
Генерируемый код проверяется компилятором, но исключён из форматирования и линта.
Workflow Хекслета сохранён без изменений и исключён из новых стилевых проверок.

Коммиты: Conventional Commits с описанием на русском, например
`chore: добавить каркас приложения`. В теле — краткое описание изменений.

## Агент в GitHub

`.github/workflows/opencode.yml` запускает OpenCode-агента в GitHub Actions: он отвечает
на команды доверенных участников в комментариях к issues и PR. Назначение — разбирать
и объяснять issues, отвечать на вопросы по коду и настройкам прямо в обсуждении;
результат — комментарий `opencode-agent[bot]` и прогон в Actions (ссылка `[github run]`
в комментарии).

- **Событие:** только `issue_comment` типа `created`; редактирование комментариев прогон
  не запускает.
- **Команды:** заданы явно input-ом `mentions: /opencode,/oc`; текст после фразы — постановка задачи.
  Гейт воркфлоу чувствителен к регистру, поэтому команды фиксируем строчными. Пример вызова: `/oc explain this issue`.
- **Фильтр запуска:** автор комментария — доверенный участник (`OWNER`, `MEMBER` или `COLLABORATOR`),
  логин без `[bot]` — команды ботов игнорируются. Недоверенные авторы (внешние
  участники и форки) job не запускают, поэтому секреты к ним не попадают;
  встроенная проверка экшена дополнительно требует write/admin-доступ у автора команды.
- **Модель:** `opencode/qwen3.8-flash` через OpenCode Console (zero-retention); ключ —
  repository secret `OPENCODE_API_KEY`, передаётся в step через `env`.
- **Авторизация и права:** стандартный OIDC-режим: `contents: read`, `id-token: write`,
  checkout с `persist-credentials: false`. Агент работает installation-токеном GitHub App
  `opencode-agent` — его права шире блока `permissions:`, поэтому границы сценария задают
  фильтр запуска и  команды, а  не только права.
- **Разрешения tools в  CI:** обработчик `opencode github run` permission-запросы
  своей сессии не отвечает, а  у  агента `build` по  умолчанию `ask` внешние пути
  и  `doom_loop` — не отвеченный запрос висит до  тайм-аута (прогон 44997541687).
  Env `OPENCODE_CONFIG_CONTENT` ставит обоим `deny`: инструмент мгновенно
  получает отказ, и  агент продолжает ответ.
- **Публикация тикетов агентом:** обработчик V1 не передаёт installation-токен
  приложения в  окружение bash-инструмента, поэтому `gh` в  прогоне работает
  раннеровым токеном: в  `permissions` добавлено `issues: write`, на  шаг экшена
  передан `GH_TOKEN`. Созданные агентом issue публикуются от  `github-actions[bot]`,
  а  ответы в  комментарии по-прежнему пишет приложение `opencode-agent`
  через  OIDC-обмен.
- **Гигиена прогона:** `timeout-minutes: 15`; одна очередь `concurrency`
  (`opencode-issue-agent`, `cancel-in-progress: false`) ограничивает параллельные запуски.
- **Share:** публичных ссылок на сессии не создаётся — явный `share: false` и прекращённый
  в CI-сборке session sharing; доказательство работы — журнал прогона и комментарий бота.
- **Скиллы и настройки:** после checkout раннер видит `.agents/skills/` (вендорный набор
  `mattpocock/skills`) и  `docs/agents/`, поэтому отвечает по конфигурации трекера
  и  правилам репозитория.

CI-экшен исполняет OpenCode V1-линейки — так устроена интеграция; локальный V2 это не
затрагивает. `opencode.json` в репозитории намеренно нет: конфиг CI-агента целиком живёт
в файле воркфлоу.

### Установка и воспроизведение

GitHub App <https://github.com/apps/opencode-agent> установлен только на этот репозиторий,
ключ Console записан в repository secret `OPENCODE_API_KEY`. Для воспроизведения на новом
репозитории:

1. Установить App из галереи, выбрав один репозиторий.
2. Записать ключ: `gh secret set OPENCODE_API_KEY` (или Settings → Secrets and variables →
   Actions).
3. Замержить `.github/workflows/opencode.yml` в `main`.

Проверка: создать issue, оставить в нём комментарий `/oc explain this issue`, дождаться
ответа бота и найти прогон `opencode` во вкладке Actions.

## Релизы

[release-please](https://github.com/googleapis/release-please-action) поддерживает
одну версию приложения: корневой пакет, API, web и SDK обновляются вместе.
После изменений в `main` бот создаёт или обновляет один релизный PR с новой версией
и общим `CHANGELOG.md`. Слияние выполняется вручную после успешного CI;
следующий запуск workflow создаёт тег `vX.Y.Z` и GitHub Release.
Автоматическая публикация в npm и деплой не настроены.

Точка отсчёта релизов здесь — `v0.6.1`: тег ставится на первый коммит
`main` после переноса, а полная история выпусков 0.1.0–0.6.1 остаётся
[в исходном проекте](https://github.com/AndrewVdovichenko/ai-for-developers-project-386/blob/main/CHANGELOG.md).
Новый `CHANGELOG.md` появится в первом релизном PR этого репозитория.
Генерируемые `CHANGELOG.md` и manifest версий исключены из oxfmt:
их формат поддерживает release-please.
Затем `fix:` повышает patch, `feat:` — minor, `perf:` — patch.
Несовместимые изменения обозначаются `!` после типа/области или футером
`BREAKING CHANGE:`: до `1.0.0` они повышают minor, после — major.
Обычные `chore:`, `docs:`, `test:` и `ci:` самостоятельно релиз не создают.
При squash merge сохраняйте Conventional Commit в итоговом заголовке
и футер несовместимых изменений в теле коммита.

### Настройка бота

Workflow использует короткоживущий installation token GitHub App, чтобы
релизный PR автоматически запускал существующие проверки GitHub Actions.

GitHub App уже создан в исходном проекте: здесь достаточно установить
его на репозиторий (шаг 3) и прописать переменную с секретом
(шаги 4–5).

1. В [настройках GitHub Apps](https://github.com/settings/apps/new) создайте App
   под своим аккаунтом. Укажите уникальное имя, адрес этого репозитория
   в Homepage URL, отключите webhook; OAuth и callback URL не нужны.
2. Выдайте Repository permissions: **Contents**, **Pull requests**, **Issues** —
   **Read and write**. **Metadata** остаётся **Read-only**; остальные права не нужны.
   App должна устанавливаться только вашим аккаунтом.
3. В Install App установите её только для этого репозитория.
4. В General скопируйте **Client ID**. В репозитории откройте
   **Settings → Secrets and variables → Actions → Variables** и создайте
   `RELEASE_PLEASE_APP_CLIENT_ID` с этим значением.
5. В General приложения нажмите **Generate a private key**. Содержимое
   скачанного PEM-файла сохраните целиком в repository secret
   `RELEASE_PLEASE_APP_PRIVATE_KEY` через вкладку **Secrets**.
   Закрытый ключ не добавляйте в репозиторий и не передавайте в переписке.

После настройки и слияния конфигурации в `main` проверьте workflow
**release-please** и созданный PR: все четыре версии должны совпадать,
а обычный workflow **check** должен запуститься автоматически.
Не редактируйте релизные версии вручную и не удаляйте служебные метки
`autorelease: pending` и `autorelease: tagged`: по ним бот отслеживает выпуск.

### Повтор после сбоя

При ошибке доступа проверьте установку App, её права, Client ID и актуальность
закрытого ключа. Исправьте настройки и повторите неудачный запуск
через **Re-run failed jobs**, либо запустите workflow **release-please** вручную
для ветки `main`. Он продолжит существующий выпуск без создания дубликатов.
Если слияние релизного PR уже выполнено, повторный запуск должен создать
недостающий тег и GitHub Release; новый релизный PR вручную создавать не нужно.
Для остановки автоматизации отключите этот workflow в GitHub Actions.
